# Object discovery by type identity (vtables / MSVC RTTI), region walking, and structure validation

Scope: finding all instances of a C++ object type in a running 32-bit MSVC / Unreal Engine 3 process from an external C# (.NET 8, x86) tool without a known pointer path, and rejecting false positives. Each section notes whether a technique works with pure `ReadProcessMemory` (RPM) or needs injection.

Source-quality legend: [P] = peer-reviewed paper (numbers taken from the PDF text), [V] = vendor or compiler-runtime source, [C] = community forum or blog (lower confidence). "Background (unsourced)" marks practitioner knowledge I could not verify against a source in this session. Treat those items as hypotheses to check.

---

## 1. vtable-pointer scanning, and going from a class name to a vtable via MSVC RTTI (and what to do under /GR-)

### Takeaway
A polymorphic MSVC object stores its vfptr at offset 0. On x86 the RTTI chain is made of absolute pointers: `vtable[-1]` -> CompleteObjectLocator -> TypeDescriptor (holding the mangled name `.?AV<Class>@@`). Name -> vtable resolution can therefore be done statically: scan the module image (pure RPM) for the name string, then work back through the COL to the vtable. Once you have the vtable, scanning 4-aligned DWORDs in committed private memory for that value finds every live instance, plus some false positives such as freed objects and stale copies. Those must be rejected by validation (sections 4–6). Under /GR- there is no COL, so the vtable has to be found from code (constructor signatures) or harvested from one known-good instance and stored module-relative.

### Cited Findings
- [V] RTTI is emitted only for polymorphic classes (classes with virtual functions). The CompleteObjectLocator (COL) sits "just before the vftable". COL fields in order: `signature` (DWORD; the article says "always zero?"), `offset` (offset of this vtable within the complete class), `cdOffset` (constructor displacement offset), `pTypeDescriptor` (TypeDescriptor of the complete class), `pClassDescriptor` (-> RTTIClassHierarchyDescriptor). — [igorsk, "Reversing Microsoft Visual C++ Part II: Classes, Methods and RTTI", OpenRCE (2006)](http://www.openrce.org/articles/full_view/23)
- [V] RTTIClassHierarchyDescriptor: `signature`, `attributes` (bit 0 = multiple inheritance, bit 1 = virtual inheritance), `numBaseClasses`, `pBaseClassArray`. It "is shared by all COLs for a class". RTTIBaseClassDescriptor: `pTypeDescriptor`, `numContainedBases`, `where` (a PMD of `mdisp` member displacement, `pdisp` vbtable displacement or -1, `vdisp` displacement inside the vbtable), `attributes`. The companion IDC script `ms_rtti4.idc` scans an executable for vtables and names them after their classes, but "may fail with virtual inheritance". — [OpenRCE (2006)](http://www.openrce.org/articles/full_view/23)
- [V] LLVM's UBSan runtime for the MS ABI reads the locator as `((CompleteObjectLocator**)VtablePtr)-1`. It checks that both the slot and the locator are readable before dereferencing. COL layout used: `is_image_relative, offset_to_top, vfptr_offset, rtti_addr, chd_addr, obj_locator_addr`. `is_image_relative == 1` -> image-relative fields. `== 0` -> absolute pointers (`CompleteObjectLocatorAbs`). Any other value -> "Probably not a complete object locator" (reject). Image base for the relative form = `(char*)obj_locator - obj_locator->obj_locator_addr`. The class name comes from `type_info::name()`. — [LLVM compiler-rt ubsan_type_hash_win.cpp](https://codebrowser.dev/llvm/compiler-rt/lib/ubsan/ubsan_type_hash_win.cpp.html)
- [C] When a program is built as x86 with Visual Studio 2022, the COL fields "are just normal 32-Bit pointers". When built as x86_64 they are "32-Bit offsets which you add to" the module base. The final x64 field `pSelf` is "the 32-Bit offset from the module's base address" to the locator itself. Microsoft has not publicly documented these structures. — [std-proposals mailing list (2024)](https://lists.isocpp.org/std-proposals/2024/04/9646.php); [std-proposals (2025)](https://lists.isocpp.org/std-proposals/2025/06/14088.php)
- [V] Boost.DLL's MSVC type_info path also steps the vtable pointer back by one slot (`vtable_p--`) to reach the locator, and notes the signature as "always zero?" (true of x86 COLs). — [Boost dll/detail/type_info.hpp](https://eic-code-browser.sdcc.bnl.gov:443/lxr/source/include/boost/dll/detail/type_info.hpp)
- [C] An open-source RTTI class dumper treats COL signature 0 as 32-bit and 1 as 64-bit. It validates a vtable candidate by checking that the TypeDescriptor pointer is valid and that its name begins with `.?AV`. — [GrandpaGameHacker/ClassDumper (GitHub)](https://github.com/GrandpaGameHacker/ClassDumper)
- [C] MSVC mangled symbol prefixes: `??_R4` marks a Complete Object Locator, and `6B@` appears in RTTI symbol names. The chain is vftable -> COL -> type_info/TypeDescriptor and ClassHierarchyDescriptor -> base-class array. — [std-proposals (2024) thread](https://lists.isocpp.org/std-proposals/2024/04/9643.php)

### Inferences
- **Name -> vtable algorithm for a 32-bit image (pure RPM, run once per game build; can be cached by module timestamp):**
  1. Enumerate the game module (e.g., `EnumProcessModulesEx` / Toolhelp module snapshot) to get `[base, base+SizeOfImage)`, then read the whole image in one or a few RPM calls.
  2. Search the bytes for `.?AV<ClassName>@@\0` (`.?AU` for `struct`). The string is the `name` field of a TypeDescriptor. On x86 the TypeDescriptor is `{ void* pVFTable /*-> type_info vtable*/; void* spare; char name[]; }`, so TD = stringAddr - 8. (TD layout is background, unsourced: verify against the dump. A sanity check is that `pVFTable` is the same value for every TD in the image, namely `type_info::vftable`.)
  3. Search the image for DWORDs equal to TD. Each hit at address h is a candidate COL whose `pTypeDescriptor` field sits at COL+12, so COL = h - 12. Keep the candidate if `signature == 0`, `pClassDescriptor` points inside the image, and the CHD there has a sane `numBaseClasses` (small, > 0) and a `pBaseClassArray` inside the image. Several COLs per class are normal: with multiple inheritance there is one COL per vtable, distinguished by the `offset` field. The primary vtable has `offset == 0`.
  4. Search the image for DWORDs equal to COL. Each hit at address p gives vtable = p + 4, because the COL pointer is `vtable[-1]`. Validate by checking that `vtable[0..k]` all point into the module's executable section.
  5. Store the vtable as an RVA (vtable - moduleBase) so rebasing or ASLR does not break the cache.
- **Whether DD1 ships with RTTI is unknown.** Unreal Engine builds traditionally disable C++ RTTI (UE4's `bUseRTTI` defaults to false). Background, unsourced for UE3. A one-time test: search the exe for the bytes `.?AV`. Few or no hits means /GR- was used.
- **If RTTI is absent (/GR-):** (a) read the vfptr (first DWORD) from one instance already found by another route (an existing pointer chain or UE3's object array), then store `vfptr - moduleBase`. (b) Signature-scan for the constructor, which writes the vtable with `mov dword ptr [ecx], imm32` (bytes `C7 01 <imm32>`) or `mov dword ptr [esi], imm32` (`C7 06 <imm32>`), and extract the imm32. (c) In UE3 the engine's own reflection (UClass objects, FName-named via GNames) gives a name -> UClass mapping that is more robust than C++ vtables. All three are background, unsourced.
- **UE3 caveat (important for game objects).** UnrealScript-only subclasses have no C++ class of their own, so they share the vtable of their nearest native parent. A vtable scan therefore returns a superset (every object whose native class matches), and you have to discriminate with the UObject `Class` pointer. Background, unsourced, but it follows from how UE3 script classes work.
- **vtable scan algorithm (pure RPM):** for every committed, readable, private region (section 2), read it in chunks, reinterpret the bytes as `uint` (in C#, `MemoryMarshal.Cast<byte,uint>`, optionally `Vector<uint>` compare), and test each 4-aligned slot against a `HashSet<uint>` or sorted array of target vtables. Heap and allocator blocks are at least 8-aligned on 32-bit Windows (background), so an 8-byte stride is possible but riskier. Each hit is only a candidate (section 4).
- The scan finds freed-but-not-overwritten objects as well. SigGraph observed exactly this (section 4), so "vtable matches" must never be the only check.

### Gaps
- I did not retrieve an authoritative source for the x86 TypeDescriptor layout (`pVFTable`, `spare`, `name`). OpenRCE only refers to it by pointer. The layout above is background knowledge.
- I could not confirm whether UE3 (DD1's 2010–2011 build) was compiled with /GR or /GR-.
- I did not retrieve the Hex-Rays/IDA ClassInformer plugin source, so its exact COL-validation heuristics are not documented here.

## 2. Region enumeration from an external process (VirtualQueryEx, Toolhelp32 heap APIs, batching, vanishing regions)

### Takeaway
Walk the address space with `VirtualQueryEx`. Keep `State == MEM_COMMIT`, `Type == MEM_PRIVATE`, and a readable `Protect` without `PAGE_GUARD` or `PAGE_NOACCESS`. Read each region in large chunks, never byte-by-byte. Microsoft itself calls `Heap32First`/`Heap32Next` inefficient for large heaps. Those APIs also only see NT heaps, while UE3 objects largely live in allocator pools obtained by direct `VirtualAlloc` (background), so region walking is both faster and more complete. Everything here is pure RPM / `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`.

### Cited Findings
- [V] `MEMORY_BASIC_INFORMATION` fields: `BaseAddress`, `AllocationBase` (base of the VirtualAlloc range), `AllocationProtect`, `RegionSize` ("region beginning at the base address in which all pages have identical attributes"), `State`, `Protect`, `Type`. `State`: `MEM_COMMIT` 0x1000, `MEM_RESERVE` 0x2000, `MEM_FREE` 0x10000. `Type`: `MEM_PRIVATE` 0x20000, `MEM_MAPPED` 0x40000, `MEM_IMAGE` 0x1000000. For free pages the other fields are undefined, and for reserved pages `Protect` is undefined. An explicit `MEMORY_BASIC_INFORMATION32` exists for cross-bitness debuggers. — [Microsoft Learn: MEMORY_BASIC_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-memory_basic_information)
- [V] `Heap32First`/`Heap32Next` are documented as inefficient, especially for large heaps. Microsoft points to `HeapWalk` as a far more efficient alternative, but `HeapWalk` only works on the calling process. The Toolhelp heap functions work cross-process by doing the in-process collection on the caller's behalf. — [Microsoft Learn: Traversing the Heap List](https://learn.microsoft.com/en-au/windows/win32/toolhelp/traversing-the-heap-list); [CreateToolhelp32Snapshot (TH32CS_SNAPHEAPLIST)](https://learn.microsoft.com/en-us/windows/desktop/api/TlHelp32/nf-tlhelp32-createtoolhelp32snapshot)
- [C] Byte-by-byte RPM is the classic performance trap: one poster reported ~50 s to scan ~70 MB across 500+ pages. Filtering regions with `VirtualQueryEx` and reading each region into one buffer is reported to bring a pattern scan under 10 s, usually under 2 s. The sample code in that answer reportedly inverts the `MEM_COMMIT` test, so verify before copying. — [CodeProject forum](https://forum.codeproject.com/post/692128); [Stack Overflow mirror: "ReadProcessMemory for a 64 bit process takes hours"](https://windows-hexerror.linestarve.com/q/so55801144-readprocessmemory-for-a-64-bit-process-takes-hours-how-do-i-reduce-the-amount-of-time-taken)
- [C] A common filter skips non-`MEM_COMMIT` regions and regions with `PAGE_GUARD`, `PAGE_NOACCESS`, `PAGE_READONLY`, or `PAGE_EXECUTE_READ`. — [CodeGuru forum](https://forums.codeguru.com/showthread.php?p=1806451)
- [C] Reads that run past the end of a region fail with Win32 error 299 (`ERROR_PARTIAL_COPY`). Clamp each read to `BaseAddress + RegionSize`. — [python-forum.io thread](https://python-forum.io/thread-5517.html)

### Inferences
- **Recommended walk (C#):** `addr = 0x10000`. Loop `VirtualQueryEx(h, addr, out mbi32, 28)` (use the 32-bit struct layout for an x86 target from an x86 process). Accept the region if `State==MEM_COMMIT && Type==MEM_PRIVATE && (Protect & (PAGE_READWRITE|PAGE_WRITECOPY|PAGE_EXECUTE_READWRITE))!=0 && (Protect & (PAGE_GUARD|PAGE_NOACCESS))==0`. Then `addr = BaseAddress + RegionSize`, and stop at the 2 GB (or 4 GB if large-address-aware) user-space limit. `MEM_PRIVATE` + RW is where heap and allocator objects live. `MEM_IMAGE` RW (`.data`) holds globals such as the UE3 global object array header and is worth scanning separately for "static root" pointers.
- **Batching:** read regions in fixed chunks (e.g., 256 KB–1 MB) into a reused pooled buffer. Overlap chunks by `structSize - 4` bytes only if validation needs the whole struct inside the buffer. Otherwise issue a second small RPM for each candidate. Thread stacks are also `MEM_PRIVATE` RW, and a `PAGE_GUARD` page sits at each stack's growth edge. Reading a guard page from another process does not trip it in the same way an in-process access would, but the filter avoids the question entirely.
- **Regions vanishing mid-scan:** treat RPM failure, or a partial read where `lpNumberOfBytesRead < requested`, as normal. On failure, re-query that address and continue from the next region. Never cache region lists across ticks; re-walk each full scan. This matches the "empty catch" race-tolerance philosophy in the consumer tool.
- **Heap32Next is the wrong tool here.** It is slow, it only sees NT heaps (UE3's `FMallocWindows` pools are separate `VirtualAlloc` blocks, background unsourced), and it does in-process work in the target. Avoid it. Raw `VirtualQueryEx` region walking is pure RPM and sees every allocator.
- Laika (section 3) found that only ~45% of a heap's address space holds active objects. The rest is allocator padding and free or uninitialized chunks, which is exactly where stale vtable values linger. Expect false-positive candidates in proportion.

### Gaps
- I found no measured benchmark of `VirtualQueryEx` + bulk-RPM throughput on a modern machine for a ~1–2 GB 32-bit process. The figures above are anecdotal forum numbers.
- I did not retrieve a primary source confirming UE3 `FMallocWindows` / binned-allocator internals (pool sizes, `VirtualAlloc` granularity).

## 3. Structure dissection and automated structure/type inference (Cheat Engine, ReClass.NET, Howard, REWARDS, TIE, Laika, ML)

### Takeaway
Interactive tools (Cheat Engine's Dissect Data/Structures with address groups, ReClass.NET) are the practical way to learn a layout from live instances by diffing group A against group B. The academic inference systems split into dynamic, execution-trace-based approaches (REWARDS, Howard, which need instrumentation, i.e., injection or emulation), static binary type inference (TIE), and pure memory-image approaches (Laika; DeepMem in section 4). The memory-image ones are the only ones compatible with pure RPM, and they are much less accurate (Laika: 32% FP / 35% FN as measured by Dolan-Gavitt et al.).

### Cited Findings
- [V] Cheat Engine's Dissect data/structures "examine[s] or compare[s] data in similar memory regions or structures" (e.g., "your character's structure with the enemy's structure"). "Add extra address" adds comparison columns. You can "right-click on an address and sort them into groups" to "compare the values in every structure and also see if the values are the same in the same group" (example: two enemy units vs two friendly units). "Automatically guess offset types" auto-types the fields. — [Cheat Engine wiki: Dissect data/structures](https://wiki.cheatengine.org/index.php?title=Help_File:Dissect_data/structures)
- [C] Guided Hacking markets a "Commonality Scanner" that automates finding all objects and classes sharing a common data structure. This is promotional material, so the claims are unverified. — [Guided Hacking (Patreon)](https://www.patreon.com/guidedhacking/posts/cheat-engine-144928574)
- [P] **Laika** (Cozzie, Stratton, Xue, King; OSDI 2008) uses Bayesian unsupervised learning on a raw memory image, on the premise that "memory images consist of many copies of a relatively small number of templates". Each machine word is classified into a block type: *address* (points into heap/stack), *zero*, *string*, or *data*. Objects with similar block-type vectors are then clustered, and "typed pointers" (the class of the pointee) refine the classes. Measured heap statistics: <1% of pointers unaligned; only 1% of integers and 3% of strings look like heap pointers; ~80% of pointers point to the head of an object; only ~45% of heap address space holds active objects; only ~30% of objects contain a pointer. Laika's polymorphic-botnet detector was >99% accurate vs ClamAV's 85%. — [Laika, OSDI 2008 (PDF)](https://www.usenix.org/legacy/events/osdi08/tech/full_papers/cozzie/cozzie.pdf)
- [P] For instance-finding, Laika's generality costs accuracy. Dolan-Gavitt et al. report Laika's false-positive and false-negative rates as 32% and 35%, against 0 FP / 0 FN for their own signature scanner. — [Dolan-Gavitt et al., CCS 2009 (PDF)](https://www.cs.columbia.edu/~brendan/ccs09_siggen.pdf)
- [P] **REWARDS** (Lin, Zhang, Xu; NDSS 2010) tags each memory location the program touches with a timestamped type attribute and propagates it along runtime data flow. Types resolve at "type sinks" (e.g., syscall or known-library arguments) and propagate backward under timestamp constraints, which separates variables that reuse the same memory. Accuracy on exercised data: ~97% average for stack variables, heap types "perfectly match" when exercised, >85% for globals. Applications include memory-image forensics. It runs under PIN, so it requires instrumentation. — [REWARDS, NDSS 2010 (PDF)](https://www.cs.purdue.edu/homes/xyzhang/Comp/ndss10.pdf); [NDSS page](https://www.ndss-symposium.org/ndss2010/automatic-reverse-engineering-data-structures-binary-execution)
- [P] **Howard** (Slowinska, Stancescu, Bos; NDSS 2011) recovers data structures from stripped C binaries by dynamic analysis in a QEMU-based emulator, tracking how memory is accessed through base pointers. It handles arrays, nested arrays, and structs (detecting arrays from loop-driven pointer arithmetic) and generates partial symbol tables. Its evaluation classifies results as correct / flattened (nested struct fields counted as outer fields) / missed / unused (never accessed during tests). Coverage of exercised code is the limiting factor. — [Howard, NDSS 2011 (PDF)](https://www.ndss-symposium.org/wp-content/uploads/2017/09/slow.pdf). The later DSIbin work notes that Howard's inferred types are often too coarse. — [DSIbin (VU Amsterdam)](https://research.vu.nl/en/publications/dsibin-identifying-dynamic-data-structures-in-cc-binaries/)
- [P] **TIE** (Lee, Avgerinos, Brumley; NDSS 2011) does principled, constraint-based type reconstruction over a type lattice that works statically or dynamically. Evaluated on 87 coreutils programs against REWARDS and Hex-Rays, it is "more conservative and up to 45% more precise". — [TIE, NDSS 2011 (PDF)](https://users.ece.cmu.edu/~aavgerin/papers/tie-ndss-2011.pdf)

### Inferences
- **Group-diff workflow (pure RPM; maps directly to CE's groups):** collect N instances of the same type (e.g., several heroes or enemies from a vtable scan). For each 4-byte offset, compute across instances: constant? zero-or-constant? pointer into the module? pointer into private memory? float in a plausible range? small integer? Offsets that are constant across group A and differ from group B identify discriminators (e.g., team or faction, class ID). Offsets that are pointers to objects with a known vtable become graph edges (SigGraph-style, section 4). This is essentially Laika's block-typing (address / zero / string / data) applied to a known type with labeled groups instead of unsupervised clustering.
- REWARDS and Howard are offline research aids at best for this project. Both need DBI or emulation of the game, i.e., injection. TIE is a static aid. None is suitable for the shipped external tool.
- Laika's statistics give priors for pointer heuristics in a 32-bit heap. "Value looks like a heap pointer" has a ~1–3% chance of coming from a random int or string, so a single pointer check is weak. Require several pointer fields, or dereference and check the target's own vtable or type.

### Gaps
- I did not retrieve ReClass.NET documentation. Its feature set (class nodes, pointer previews, memory-diff highlighting) is not cited here.
- I did not check whether the Cheat Engine wiki documents how "Automatically guess offset types" decides pointer vs float vs string.
- Newer ML-based type inference for binaries (e.g., neural decompiler type recovery) was not surveyed beyond DeepMem (section 4). I found no ML work aimed specifically at user-mode game objects.

## 4. Robust data-structure signatures from memory forensics (Dolan-Gavitt CCS'09, SigGraph NDSS'11, Volatility pool scanning, DeepMem CCS'18) and how they transfer to game objects

### Takeaway
The forensics literature converges on three ideas. (1) Constrain only fields the program cannot run without. Dolan-Gavitt et al. found hand-picked signatures used fields the OS never reads, while profiled and fuzzed "essential" fields produced 0 FP / 0 FN. (2) Use pointer topology (points-to graphs) as well as values. SigGraph scanned 16/23 Linux structures perfectly vs 5/23 for value invariants. (3) Combine many weak voters with a reward for cross-validation. DeepMem reached >99.5% precision and recall on EPROCESS and ETHREAD. All of these work on a raw memory snapshot, so they port to a pure-RPM scanner.

### Cited Findings
- [P] **Dolan-Gavitt, Srivastava, Traynor, Giffin, "Robust Signatures for Kernel Data Structures", CCS 2009.** Pipeline: (1) *profile* which fields of the structure the OS reads or writes, using hypervisor page-access monitoring. (2) *Fuzz* the frequently accessed fields in a VM with four patterns (zero, random, random-primitive-of-type, random-aggregate i.e. a pointer to another valid structure of the right type), wait 30 s, and test whether the OS or program still works. (3) Infer constraints on the surviving robust fields from a training corpus using templates: *zero subset* (zero allowed as an OR case), *constant*, *bitwise AND* (bits common to all values, e.g., kernel pointers have the top bit set), and *alignment* (a power-of-two divisor). (4) Emit a Volatility scanner plugin. — [CCS 2009 (PDF)](https://www.cs.columbia.edu/~brendan/ccs09_siggen.pdf)
- [P] Quantitative results (same paper): of EPROCESS's **221 fields**, 32 were never accessed across 20 profiled programs and 72 were accessed by every program. The 72 were fuzzed 4 patterns × 5 times = **1,440 tests**. 5 fields failed every manipulation, 12 more failed more than half, and **29 passed every test** (attacker-controllable, so useless for signatures). The signature used the **15 most robust fields**, with constraints learned from 184 processes in 4 Windows XP SP2 images. Example constraints: `Pcb.ThreadListHead.Flink: val & 0x80000000 == 0x80000000 && val % 8 == 0`, `VadRoot: val & 0xc0003000 == 0xc0003000 && val % 0x1000 == 0`, `Token.Object: val == 0 || (val & 0x80000000 == 0x80000000 && val % 8 == 0)`. On NIST CFReDS images all three scanners found every process with no false positives, but only the robust scanner found the DKOM-hidden process. Only **2 of PTFinder's 9** hand-chosen features were evasion-resistant (3 were fields the OS never reads). Earlier work showed "changing a single bit in the Windows process data structure was sufficient to evade all known signatures". — [CCS 2009 (PDF)](https://www.cs.columbia.edu/~brendan/ccs09_siggen.pdf)
- [P] Lesson on object lifecycle (same paper): the robust scanner *missed terminated processes* that other tools found, because Windows zeroes `Token.Object` and `Token.Value` on exit. Dropping those two constraints recovered them without adding false positives. "The terminated processes demonstrate the importance of generating signatures from a training set that represents the full range of objects one wishes to detect." — [CCS 2009 (PDF)](https://www.cs.columbia.edu/~brendan/ccs09_siggen.pdf)
- [P] **SigGraph (Lin, Rhee, Zhang, Xu, Jiang; NDSS 2011)** builds graph signatures rooted at a struct, with edges given by pointer fields at fixed offsets. The "immediate pointer pattern" is `IPP(T) = f1·t1·(f2−f1)·t2·…`. Patterns are expanded layer by layer (BFS) until unique among all types, to avoid isomorphic false matches. The generated scanner is `assertPointer(*(x+off))` recursively down the graph. Over 40% of Linux 2.6.18 structures have pointer fields, ~88% of those have unique signatures, and ~12% cannot be made unique because of isomorphism. Practical refinements from long profiling runs (hours to tens of hours): exclude `void*` and union pointer fields, exclude any field ever observed NULL or non-pointer, and allow special sentinel values (LIST_POISON 0x00100100 / 0x00200200). — [SigGraph, NDSS 2011 (full paper PDF)](https://friends.cs.purdue.edu/pubs/NDSS11.pdf); [NDSS slides](https://www.ndss-symposium.org/wp-content/uploads/2017/09/lin1.pdf)
- [P] SigGraph accuracy: across 23 kernel data structures, with freed-but-not-reallocated objects counted as false positives, SigGraph identified all instances of **16** perfectly (0 FP, 0 FN) vs **5** for value-invariant signatures. Excluding freed objects, **20 vs 9**. SigGraph had no false negatives, and its FP rate was equal or lower in every case except `dentry`. Brute-force scanning "can further identify freed-but-not-yet-reallocated objects". Cost: some scanners took ~15 minutes on a 256 MB image. — [SigGraph full paper](https://friends.cs.purdue.edu/pubs/NDSS11.pdf)
- [V/C] Volatility's pool scanner matches Windows pool-header constraints (tag, pool type, size, index) before applying object-specific checks. A Volatility maintainer notes that psscan "is like a carver for processes so sometimes it gives a false positive". — [Volatility 3 poolscanner API docs (mirror)](https://foobarv3.readthedocs.io/en/latest/volatility.plugins.windows.poolscanner.html); [vol-users mailing list](https://lists.volatilityfoundation.org/mailman3/hyperkitty/list/vol-users@lists.volatilityfoundation.org/thread/SDVWHKZTOL22PB3TPPJQRVYSMLEINTD3)
- [P] **DeepMem (Song, Yin, Liu, Song; CCS 2018)** builds a memory graph (nodes = pointer-delimited segments, edges = pointers) with ~1.33 M nodes and ~5.3 M edges per dump, embeds it with a graph neural network, and detects objects by *weighted voting*. Each node label contributes the weight `count(c,l)/count(c)`, plus a reward `|L(s,c)| − 1` for addresses voted by multiple independent voters, because "it is less likely that two different voters both make errors and vote for the same address". The threshold is tuned for best F-score. Results: >99.5% precision and recall for `_EPROCESS` and `_ETHREAD`. Smaller objects scored worse: `_FILE_OBJECT` (128 B) 98.17% precision, `_CM_KEY_BODY` (44 B) 95.44%. A 1 GB dump becomes a graph in ~80 s, then ~13 s per type on a Core i7-6700 without a GPU. It is robust to pool-tag manipulation and DKOM, which defeat Volatility's signature scans. Only 1.32% of `_EPROCESS` objects sat at the same virtual address across dumps (4.7% for `_ETHREAD`), which is why fixed addresses do not transfer. — [DeepMem, CCS 2018 (PDF)](https://www.cs.ucr.edu/~heng/pubs/deepmem_ccs18.pdf)

### Inferences
- **Translating to game objects (pure RPM).** A "Hero" signature in this style would be a conjunction of *robust* field constraints plus graph edges:
  - `+0x00 vfptr ∈ {known vtable RVAs + moduleBase}` (constant template). For UE3 script classes, also `Class == <UClass* for Hero>` (constant).
  - Pointer fields (`Outer`, `Class`, owner/controller, inventory array data pointer) satisfy `val == 0 || (val in committed private memory && val % 4 == 0)` (zero-subset + alignment + "AND"-style range). Dereference one or two levels and check that the target's vfptr is the expected type (SigGraph edges).
  - Name: FName index `0 <= idx < GNames.Num` and `GNames[idx]` non-null (range + edge).
  - Scalars: health ∈ [0, 1e7], level ∈ [1, 100] as finite floats and ints. Range checks are value invariants, and per Dolan-Gavitt they are only robust if the game cannot run without them being sane. Prefer fields the engine *reads every tick* (e.g., location, health) over cosmetic or unused ones.
  - TArray header `{Data*, Num, Max}`: `0 <= Num <= Max <= sane cap`, and `Data == 0` iff `Max == 0`. This is a cheap, strong structural invariant common in UE3 (background, unsourced).
- **"Profiling" substitute:** without a hypervisor, approximate Dolan-Gavitt's profiling by sampling many live instances over time (and across sessions or levels) and keeping only fields whose constraint holds in *every* sample. That is their constraint-template step applied to user-mode data. Include dying, respawning, and default or archetype instances in the training set, per the terminated-process lesson.
- **Expected false-positive sources in UE3 specifically** (background, unsourced): class default objects (`Default__<Class>`) and archetypes share the vtable and Class of real instances, so filter them by object flags or name. Freed objects whose memory has not been reused still hold the old vtable (SigGraph's "freed-but-not-reallocated"). Pending-kill or destroyed actors may still be in memory with flags set.
- DeepMem's object-size trend (smaller objects, lower precision) suggests that for small structs you should lean harder on graph edges and the vtable than on value ranges.
- Cost trade-off: value-invariant checks are cheap and run on every vtable hit. Graph checks cost 1–2 extra RPMs per candidate, but vtable pre-filtering makes the candidate count small, so SigGraph-level rigor is affordable here even though full brute-force SigGraph scanning was slow (~15 min per 256 MB) in the paper.

### Gaps
- I did not read Volatility source (`poolscanner.py`, `psscan`) directly. Exact per-check logic (e.g., pool-header size and type checks) is not quoted.
- No paper found applies these signature-generation techniques to game or user-mode application objects specifically.

## 5. Heuristic validation patterns for candidates (pointer validity, back-pointers, invariants, cross-object consistency, scoring/voting)

### Takeaway
Validate each vtable hit with a layered, cheap-to-expensive checklist: in-buffer value checks, then pointer-range checks against a cached region map, then one-hop dereferences (target vtable, back-pointer, self-index), then cross-object consistency. Accept on a conjunction of hard invariants, or on a weighted score with a bonus for independent agreement (DeepMem style). Every pattern below is pure RPM.

### Cited Findings
- [P] Pointer-validity templates that worked: "bitwise AND" (all values share high bits, i.e., the pointer lies in a known address range) and "alignment" (power-of-two divisibility). Zero is handled as an explicit OR case rather than rejected. — [Dolan-Gavitt et al., CCS 2009](https://www.cs.columbia.edu/~brendan/ccs09_siggen.pdf)
- [P] A NULL pointer cannot be told apart from an integer zero. Treating 0 as a valid pointer makes an all-zero region match every pointer pattern, so SigGraph only asserts pointer-ness on fields never observed NULL during profiling. — [SigGraph, NDSS 2011](https://friends.cs.purdue.edu/pubs/NDSS11.pdf)
- [P] Heap priors: <1% of pointers are unaligned and ~80% of pointers point to an object head, so "points to the start of an object with a valid vtable" is a strong test. — [Laika, OSDI 2008](https://www.usenix.org/legacy/events/osdi08/tech/full_papers/cozzie/cozzie.pdf)
- [P] Weighted voting plus a cross-validation reward for multiple independent voters agreeing on the same address, with the threshold tuned on validation data for best F-score. — [DeepMem, CCS 2018](https://www.cs.ucr.edu/~heng/pubs/deepmem_ccs18.pdf)
- [V] Runtime RTTI consumers verify readability of `vtable[-1]` and of the COL before dereferencing, and reject a COL whose signature is not 0 or 1. — [LLVM ubsan_type_hash_win.cpp](https://codebrowser.dev/llvm/compiler-rt/lib/ubsan/ubsan_type_hash_win.cpp.html)
- [C] In UE3, a global object array (GObjects) holds pointers to all UObjects, and UE3 SDK generators locate GObjects and GNames by offsets or byte patterns. — [DEV Community: Rocket League (UE3) reverse engineering](https://dev.to/drkn1ght/how-to-extract-rocket-league-data-in-real-time-reverse-engineering-in-unreal-engine-games-505l); [RLSDK-Generator (UE3)](https://github.com/matix2/RLSDK-Generator)

### Inferences
- **Layered validator for a 32-bit UE3 candidate at address `a`** (cheap to expensive, short-circuit on failure):
  1. `a % 4 == 0`. `vfptr ∈ targetSet`. Optionally `vfptr` lies in the module's `.rdata`.
  2. Read the whole struct with **one RPM** (section 6).
  3. Value invariants on robust fields (ranges, zero-or-aligned pointers, TArray `Num <= Max`, finite floats with NaN/Inf rejected).
  4. Pointer fields fall inside a *cached sorted list of committed regions* from the last walk: a binary search, no syscall. Laika's priors make a single pointer check weak, so require several.
  5. One-hop edges: `Class->vfptr == UClass vtable`. `Outer` is null or a valid UObject. For an owner/controller pair, `Controller->Pawn == a` (a **back-pointer**, which is very strong because random data almost never points back).
  6. **UE3 self-index invariant** (background, unsourced but standard UE3): `GObjects.Data[obj->Index] == a`. This one check proves the object is live and registered, rejects freed copies, and doubles as a generation check (section 6).
  7. Reject CDOs and archetypes: name starts with `Default__`, or the class-default flag is set.
- **Scoring vs conjunction:** use hard conjunctions for structural invariants (vtable, self-index, back-pointer), which almost never hold by accident. Use weighted scores for soft value ranges (health, level), which legitimately go out of range during death or spawn and would otherwise cause false negatives.
- **Cross-object consistency:** the instance count should match a game-side count where one exists (e.g., the party size, or the length of the world's pawn list). Every hero found should be reachable from the world's actor list, or explicitly flagged as orphaned. This is the "view comparison" method SigGraph and DeepMem use for rootkit detection (scan results vs list walk), applied here as a correctness cross-check rather than hidden-object detection.

### Gaps
- No authoritative UE3 source was retrieved for exact UObject field order or flags (`ObjectFlags`, `Index`, `Outer`, `Name`, `Class`) in the 2010–2011 engine. Offsets must come from the project's own verified SDK.

## 6. Reliability tricks (re-validation every tick, generation counters, detecting freed/reused memory, atomic-ish whole-struct reads, double-read consistency)

### Takeaway
Treat every cached address as a hypothesis. Re-check a cheap fingerprint (vfptr + self-index + one invariant) every tick, from one RPM per object. Treat any mismatch as "freed or reused": evict it and let a periodic re-scan rediscover it. For values you write or display, use a whole-struct single read plus an optional double-read compare to avoid acting on torn or transitional state. All of this is pure RPM. Only "never torn" guarantees would need injection (code running on the game thread).

### Cited Findings
- [P] Object addresses do not survive across runs or reallocation: only 1.32% of `_EPROCESS` objects (4.7% of `_ETHREAD`) occupied the same virtual address across dumps. — [DeepMem, CCS 2018](https://www.cs.ucr.edu/~heng/pubs/deepmem_ccs18.pdf)
- [P] Freed-but-not-yet-reallocated objects remain in memory and match structural signatures. SigGraph explicitly reports FP counts with and without them. — [SigGraph, NDSS 2011](https://friends.cs.purdue.edu/pubs/NDSS11.pdf)
- [P] Objects change shape over their lifecycle (Windows zeroes token fields when a process exits), so a validator tuned only on live objects misses or rejects transitional ones. — [Dolan-Gavitt et al., CCS 2009](https://www.cs.columbia.edu/~brendan/ccs09_siggen.pdf)
- [C] A read that crosses into an unmapped or decommitted page fails or returns a partial copy (`ERROR_PARTIAL_COPY`, 299). — [python-forum.io thread](https://python-forum.io/thread-5517.html)

### Inferences
- **Per-tick re-validation (cheap):** for each cached object, one RPM of the header plus the fields needed. Check `vfptr` unchanged, `GObjects[Index] == addr` (UE3), and `Class` unchanged. If any fails, the slot was freed or reused, so drop it. A changed vtable is the classic reuse signal: the memory now holds a different type. An unchanged vtable but a failed self-index means a freed copy or a stale CDO.
- **Generation counters:** UE3 has no explicit per-object generation counter in 2010-era builds (background, unsourced; UE4 later added serial numbers to its object array). The tuple `(addr, Index, Name)` acts as a pseudo-generation. If any element changes, the identity changed. Store that tuple with each cached handle.
- **Re-scan cadence:** a full vtable scan is O(private RW bytes). Run it on events (level load, party change, a validation failure, or "count mismatch" from section 5) or every few seconds, not every 50 ms tick. Between scans, rely on per-tick re-validation.
- **Atomic-ish reads:** read the whole struct (or the contiguous span you need) in a single RPM so fields come from roughly one instant. That is not atomic, since the kernel copies while game threads run. Individual aligned 4-byte values are never torn on x86 (background), but multi-field relationships can be. For safety-critical writes (e.g., before writing to an object), do a **double read**: read, then read again; proceed only if the identity fields (vfptr, Index, Class) and the targeted field are equal in both. If not, skip this tick.
- **Write-side guard:** immediately before `WriteProcessMemory`, re-read the vfptr and self-index in the same tick. Writing into a reused slot is the main way an external editor corrupts or crashes the game. A pre-write fingerprint check closes most of that window, though not all of it (TOCTOU remains without injection).
- **What needs injection:** a truly consistent snapshot (pausing game threads, or running on the game thread) and hooking allocation and free to track object lifetimes exactly. SigGraph's profiler hooked `kmem_cache_alloc`/`free` for this, and the in-game analogue would be hooking UObject construction or destruction. Everything else above works externally.

### Gaps
- No source was found that measures torn-read rates or a recommended double-read policy for external game-memory tools. These recommendations are engineering inference.
- No source was found confirming whether DD1's UE3 build has per-object serial numbers or any other generation mechanism.
